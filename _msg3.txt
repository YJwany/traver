fix(geo): resolve Chinese destinations to the right city

Found by measuring OSM coverage for Chinese cities after comparing this project
with 1sdv/TripStar. The coverage question turned out to be the wrong question:
major Chinese cities are well mapped (six of six saturated the per-category
limits), but the resolver was returning confidently wrong coordinates for the
destinations that mattered.

Three defects, all silent - each produced a plausible-looking place record and
a coherent plan for a city the user never asked for:

1. A national capital ranked below a county seat. `_score_open_meteo_result`
   tested `startswith("PPLA")` for the top rank, but `"PPLC"` (capital) does not
   match that prefix, so Paris, France (PPLC, population 2.1M) scored rank 1
   while Paris, Texas (PPLA2, population 24k) scored rank 2. The score tuple
   compares rank before population, so population could not compensate. 巴黎
   resolved to Kentucky, ~8,300 km away; 罗马 resolved to Georgia.

2. A wrong answer suppressed the fallback. Nominatim was only consulted when a
   source failed or returned nothing, but 丽江 returned exactly one result - a
   `PPL` with no population, in Hunan, ~1,154 km from the Yunnan city. A
   non-empty answer ended the search, so the user got a full itinerary for a
   small town in the wrong province.

3. An administrative area's centroid is not the place. 平遥 resolved to the
   centroid of 平遥县, ~11 km from 平遥古城 and therefore outside the +/-0.045deg
   search box, so the destination returned zero POIs even though OSM maps the
   old town.

The fixes:

* `_feature_rank` orders PPLC > PPLA > PPLA2..5 > PPL.
* A candidate is only trusted when it is an administrative seat *and* carries a
  real population; otherwise it is provisional and the next source is asked. A
  provisional answer is still used if nothing better is found, because an
  imperfect coordinate beats refusing to plan.
* Nominatim now requests 5 candidates (same single request) and prefers a
  settlement over an area, keyed on `addresstype` rather than `class`. The live
  jsonv2 responses carry no `class` field at all, so an earlier version of this
  change - and its test - keyed off a field that never appears. The test payload
  now mirrors the real response shape. The preference is bounded to 50 km so it
  can only refine within a locality, never jump to a distant namesake.

Measured on the real network (hotels/food/sights):

  丽江  1/0/1 -> 35/53/32      巴黎  8/30/4 -> 40/62/56
  平遥  0/0/0 -> 36/20/37      苏州  40/47/54 (unchanged)

The old implementation was stashed and re-run to confirm all three cases differ,
so the new tests fail against it rather than passing vacuously.

Verified: 298 offline tests pass (7 new), ruff check and format clean.
