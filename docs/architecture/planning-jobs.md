# 长时规划与进度推送

规划不是瞬间完成的，也无法诚实地假装它是。实测单次 Overpass 查询要 36.5 秒，而一份真实行程在对齐路线之前还要扇出到多个数据源。一个阻塞几十秒的同步请求不只是慢——它和「卡死」在用户眼里没有区别：浏览器在转，没有任何东西解释为什么，旅行者无法分辨「在干活」和「挂了」。

所以规划被排成一个作业（job），作业报告它**实际**在做什么。

## 两条承诺

**步骤是真的。** 每一步都在代码真正跨过的边界上发出，并带上它开始与结束的墙上时钟时间。由定时器驱动的进度条比没有进度条更糟：它会在什么都没发生时平滑前进，然后突然跳一下——这教会用户忽略它。这里如果什么都没动，时间戳会显示出来。

**结局是五种状态之一，失败不会被掩盖。** 规划失败就报告真实错误，而不是一份空行程；被取消的作业说它被取消了，而不是报告成功却没有数据。

## 为什么不沿用同步接口

同步接口（`POST /api/v1/trips`）保留，它适合脚本与测试。但浏览器不该用它，因为浏览器必须向用户解释等待。作业接口的价值不在性能，而在**可解释性**：

| | 同步 | 作业 |
| --- | --- | --- |
| 用户看到 | 转圈，无解释 | 当前阶段、已完成步数、每步真实耗时 |
| 慢的时候 | 无法分辨是否卡死 | 该步显示为耗时很长 |
| 页面关掉 | 请求被中断，工作白做 | 作业在服务端继续，重新打开仍能读到结果 |
| 出错 | 一个 HTTP 错误 | 失败的步骤 + 服务端原始错误信息 |

## 阶段边界

每一步对应 `build_preview` 里一个真实的阶段，不是照着接口写出来的脚本：

| 步骤 | 详情 | 说明 |
| --- | --- | --- |
| `resolve_sources` | 按属主装配可用数据源 | 未配置任何凭据时也走这里，此时源是免费源 |
| `collect_places` | 酒店、餐厅、景点、天气、节假日 | 五个能力并发 |
| `room_offers` | N 家酒店 / 无候选酒店，跳过 | 即使跳过也报出，这样步骤列表形状稳定，「没有这一步」不会被误读成静默失败 |
| `enrich_attractions` | N 个景点 / 跳过 | 只对带 OSM wikipedia/wikidata 链接的景点执行 |
| `calculate_routes` | N 个途经点 / 途经点不足，跳过 | 通常是最慢的一步，也是整个机制存在的理由 |
| `build_itinerary` | 预算与每日路线 | |
| `collect_health` | 各数据源状态 | |
| `save_trip` | 写入行程与实体 | 仅 `queue_trip=true` |

阶段是**在打开时**发布的，不是完成时——这是唯一有意义的时机。如果等完成后才发布，用户在最初那 36 秒里什么也看不到。

步骤的时间由 `started_at`/`finished_at` 两个真实读数算出；未完成的步骤 `finished_at` 为 `null`、`duration_ms` 为 `null`，前端显示「进行中」而不是 `0 ms`。`0 ms` 是一个测量结论（「瞬间完成」），而 `null` 是「还不知道」。

结合作业结束时会关闭所有仍打开的步骤，因此不会留下永久转圈的 spinner。

## 取消

- 取消是**请求**而不是命令：worker 在两个阶段之间检查，因此取消发生在可以干净放弃部分工作的边界上，而不是在写行程的中途。
- 取消在完成后到达也是**被遵守**的。runner 可能在取消请求之后正常结束；此时报告成功会与用户被告知的内容矛盾。
- 取消一个已完成的作业是**无操作**，不是错误。把双击的第二次点击变成本不存在的失败，会让用户去找一个没有的 bug。
- `CANCELLED` **不并入** `FAILED`：一个是用户的决定，另一个是问题。把取消报成失败会让用户去找 bug；报成成功则会让用户去找一份不存在的行程。

失败时 `error` 是**原始信息**（例如「高德返回了 status=0：INVALID_USER_KEY」），不是「规划失败」。这是本地规划工具而不是需要隐藏内部细节的公开 API，且那条细节是唯一让问题可修的东西。异常没有消息时回退到异常类名，避免出现空错误串。

## 属主隔离

作业携带请求者的目的地与日期，因此：

- 另一个属主读到的是 **404 而不是 403**：确认这个 id 存在本身就是泄露。
- 同一个 404 覆盖「id 不存在」与「不是你的」，两者不可区分。
- 取消也做同样的检查——否则任何人都能停掉别人的规划。

属主在**提交时捕获**，不在后台任务里重新读取。后台任务比启动它的请求活得更久，在任务里读环境变量等于按「任务恢复时恰好是谁在问」来规划。

## SSE，以及为什么不用 EventSource

`GET /api/v1/planning/jobs/{id}/events` 提供 Server-Sent Events：

- 单向流量，**SSE 比 WebSocket 更合适**：以普通 HTTP 穿过代理、断线自动重连——住酒店 wifi 的旅行者都用得上。
- 每一帧发送**整个作业快照**而不是增量。晚连上的客户端、或者重连的客户端，不可能得到与服务端不一致的进度显示。
- 流在作业到达终态时**结束**。一个永不关闭的流是只在生产环境才暴露的资源泄漏。
- 空闲 15 秒发一个 `: keep-alive` 注释帧，避免中间层关掉连接。
- 响应头带 `X-Accel-Buffering: no`，否则 nginx 会缓冲整个流，进度会在结束时一次性到达——那正是这个功能要避免的。

**前端用 `fetch` + `ReadableStream` 手工解析 SSE，而不是 `EventSource`。** `EventSource` 无法设置 `Authorization` 头，用它就意味着把 API 密钥放进查询串——那会进入服务端日志、代理日志和浏览器历史。Traver 的密钥是用户全部访问权限的载体，这个取舍不成立。

**流是便利，不是机制。** 作业是服务端的持久状态，流只省去轮询。流失败（代理缓冲、浏览器断连）时前端回落到轮询，答案依然正确。一个「流一坏就坏掉」的进度显示，比没有流式更糟。

## 实测：进度确实在流动

用真实免费数据源（Overpass / Open-Meteo / OSRM / 中文维基，无任何密钥）对「杭州 3 天」跑一次，全程 **69.8 秒**，收到 14 帧，其中 13 帧在作业结束前到达：

```
+   0.0s  [running] collect_places      collect_places(running)
+  39.1s  [running] -                   collect_places=40399ms
+  39.1s  [running] room_offers         room_offers(running)
+  39.1s  [running] -                   room_offers=1ms
+  39.1s  [running] enrich_attractions   enrich_attractions(running)
+  42.0s  [running] -                   enrich_attractions=2945ms
+  42.0s  [running] calculate_routes     calculate_routes(running)
+  69.8s  [running] -                   calculate_routes=27759ms
+  69.8s  [running] build_itinerary      build_itinerary(running)
+  69.8s  [running] -                   build_itinerary=9ms
+  69.8s  [running] collect_health       collect_health(running)
+  69.8s  [running] -                   collect_health=0ms
+  69.8s  [succeeded] -
```

这组数字本身就是这个功能存在的理由：**用户按一次按钮，等 70 秒**。其中 40.4 秒花在采集中（比先前记录的 36.5 秒还慢），27.8 秒花在算路线上。没有进度推送，这 70 秒就是一个不解释自己的转圈；有了它，用户在第 0 秒就知道在采集，在第 42 秒知道已经在算路线——而「算路线很慢」正是「路线一定要好」这条要求的代价，明说出来比藏起来诚实。

（`save_trip` 不在列表里，因为这次是 `queue_trip=false` 的纯预览；`enrich_attractions` 的 2.9 秒是抓中文维基简介。）

## 已知限制（明说）

- **注册表在进程内。** 多 worker 部署需要一个共享存储，才能让一个 worker 上创建的作业在另一个 worker 上被轮询到。把它写在这里而不是藏起来。对单进程部署，这没有会失败的外部依赖。
- 已完成作业按 `max_jobs`（默认 200）淘汰最旧的；进行中的作业**永不**被淘汰，否则正在等它的那次轮询会断。
- 没有跨重启的持久化：进程重启后作业消失，行程本身已落库。

## 顺带补上的一个洞

在做这一步之前，Web 界面创建行程的唯一入口是自然语言对话——那需要模型。因此**一个什么都没配置的旅行者根本没法从界面生成行程**，尽管 API 在零凭据下能产出完整行程。

现在 `/trips/new` 有两种方式，顺序不是随意的：「填写字段」在前，因为它零配置可用；「用一句话描述」是需要模型的增强。这把 渐进增强 从 API 层面补到了界面层面。

## 验证

- `tests/unit/test_planning_jobs.py`（19 项）：步骤时间、未完成步骤不谎报完成、失败信息、取消语义、属主隔离、淘汰策略、序列化。
- `tests/integration/test_planning_job_api.py`（17 项）：路由解析（`/planning/jobs` 不会被 `/trips/{trip_id}` 吞掉）、202 语义、真实步骤列表与耗时、失败路径、跨属主 404、SSE 内容类型与自行关闭。
- 真实 uvicorn 端到端：提交 → 202 → SSE 经 socket 逐行读取 → 8 个步骤全部关闭且都有耗时 → 行程已落库 → 无效密钥读不到作业。
- 用真实免费数据源（Overpass / Open-Meteo / OSRM）跑一次，确认进度帧是在作业**仍在进行时**陆续到达，而不是在结束时一次性到达。
