# 内容摄取（自己的内容源）

Traver 自己不带数据。而最详细的旅行信息往往不在任何 API 里：它在一篇小红书笔记、一条抖音评论、一份大众点评评价、一篇携程攻略里。这些平台**都没有公开 API**，抓取它们既违反服务条款，也意味着要持有使用者的登录态。

所以这里走的不是「数据源」，而是**摄取**：使用者把自己已经能看到的内容交给 Traver，Traver 从中提取结构化事实——而每一条事实都保持标注为「某个人说的」。

## 为什么用规则而不是模型

提取器（`services/ingestion.py`）是纯规则式的，这是设计决定而非能力不足：

- **零配置也能用**。没有接任何模型的使用者照样能拿到笔记里的价格、闭馆日与提醒，与全系统的「渐进增强」一致。若这里依赖模型，摄取这条路就只对已经配好模型的人存在。
- **每条规则说明自己的依据**。`ExtractedFact.reason` 写出「「元」紧跟数字」这类理由，所以一个读错的判断是可诊断的，而不是玄学。
- **它不会凭空补全**。让语言模型「提取事实」，它会产出笔记里根本没有的、看起来很合理的人均消费；这里在文本没说的地方就是不说，这才是规划工具需要的行为。

一个方向的偏向是刻意的：**宁可漏掉一条，也不编造一条**。漏掉一条提示让旅行者损失很小，编造一个价格让他们损失金钱。

## 五条诚实规则

| 规则 | 落地方式 |
| --- | --- |
| **声称不是测量** | 提取结果一律是 `ContentReference` / `source_type=user_provided`，永远不是 `commercial_fact`。它可以作为估算进入预算，绝不能覆盖报价 |
| **每条事实引用原文** | `evidence` 是输入中**逐字**的那一段，`char_start/char_end` 指向它。引用不出自己的事实不会被输出 |
| **置信度描述的是「读得准不准」** | 只说我们有多确定文本是这个意思，从不说我们有多确定这是真的。两者是不同的数字，混淆就把观点洗成了事实。前端文案同样受限（`识别明确` / `识别一般` / `仅为线索`，`apps/web/lib/ingestions.ts`） |
| **缺失就保持缺失** | 文本没提价格就没有价格，不是 0。一个过度积极的提取器最典型的失效就是补上读者期待的那个数字 |
| **发布时间通常缺席，而缺席要被说出来** | 页面写了日期就带上；没写就如实记为「发布时间未知」，而不是默认为「刚刚」。一条 2019 年的建议与昨天写的，在粘贴框里看起来完全一样 |

## 提取什么

| 类型 | 例子 | 说明 |
| --- | --- | --- |
| `price` | 人均 80-120 元 / 门票 ¥75 | 只在**货币标记**旁边才认。光秃秃的数字是日期、公交线路或楼层数——把它当价格是提取器凭空造预算的经典方式。区间保持为区间，不做平均 |
| `duration` | 建议游玩 2 小时 / 排队 40 分钟 | 单位由**匹配到的规则**给出，绝不从捕获组数量推断 |
| `opening_hours` | 周一闭馆 / 营业时间 09:00-17:00 | 需要「周X」与「闭馆/休息」类词**同现**。「周一」是日期，「休息」是打盹 |
| `warning` | 排队很久、宰客、避坑 | 需要具体的负面信号词。泛泛的「不太好玩」是情绪，把它升级成警告等于给一个陌生人的心情以证据的分量 |
| `tip` | 建议早点去 | 建议口吻 |
| `place_mention` | 推荐去灵隐寺 | 靠**后缀**（寺/塔/馆/湖/山/古镇/步行街…）识别。中文没有大小写也没有词边界，没有后缀约束就只是在猜任意子串 |

### 两个被测试钉住的提取陷阱

- **地名修剪**。「我昨天去了杭州西湖」最初会整句变成地名。现在按「不可能出现在地名里」的字符切分并取最后一段，得到「杭州西湖」。`和 / 与 / 及` 被**刻意排除**在这个集合之外——它们既是连词，也是真地名的首字（和平公园），当作噪声会把要清理的名字弄坏。
- **「周一闭馆」不是地名**。它以「馆」结尾，于是后缀规则把它报成了一个叫「周一闭馆」的景点——一句关于**关闭**的话变成了目的地。现在「表示这里关门的词不可能同时是它的名字」被写成规则。

## 书签小工具

`GET /api/v1/content/bookmarklet` 生成脚本。它在**使用者自己已登录的浏览器**里、在他们正在看的页面上运行，只读取标题、正文文本、作者、发布时间与网址。

- 它**不**读 cookie、localStorage、sessionStorage 或任何 token；有测试断言这些字符串不出现在脚本里（`test_the_bookmarklet_never_carries_or_asks_for_a_password`）。读它们会把一个便利功能变成凭据收集工具。
- Traver **从不**向这些域名发起请求，也不保存任何登录态。
- 脚本由服务端生成而不是写死在前端：前端再复制一份就会与它要请求的端点漂移，而失效表现是「书签某个时候开始不工作了」。
- 路径是 `/content/bookmarklet` 而不是 `/ingestions/bookmarklet`：后者有个 `/ingestions/{ingestion_id}` 兄弟路由，靠注册顺序才能正确解析——一个会因为有人重排文件而坏掉的路由。换个前缀就消除了这个隐患。

## 如何进入行程

摄取内容进入 `TripPreview.ingested_notes`，**贴着它所谈论的那个地点**：

- 匹配规则是把事实的**证据句**与已聚合实体的名称对照，其次才是提取出的地名。只用提取的地名匹配时，「住成都天际酒店」永远关联不上那家酒店——名字一直在句子里，只是「酒店」不是提取器认识的地名后缀。
- **只匹配，绝不合并**。实体的自有字段一个都不改。笔记里的价格与时长是别人的记忆和偏好；让它们写进实体，就是又一次把观点洗成事实。有测试逐字段比对前后实体（`test_a_note_never_overwrites_a_measured_entity_field`）。
- **匹配不上的提及照样报出来**。那是我们数据里的缺口，藏起来会让笔记看起来被完整利用。它以 `matched: false` 列出。
- **每条都进入引用**（`source_references`）。没有引用来源的内容，其出处无法核对。
- **排序把注意事项放前面**：闭馆日会改变能规划什么，提示不会。同样排序会把唯一能省下一个上午的事实埋掉。

## 把「文中提到的地点」落到坐标上

匹配不上的提及在过去只能以 `matched: false` 收场——它没有坐标，于是进不了路线，笔记里最具体的那部分反而完全用不上。现在这些地名会被地理编码，结果进入 `TripPreview.ingested_places`。

这条路的每一步都在防止同一个错误：**一个被念出来的名字，被当成一个被测量出来的地点**。

### 它是另一种东西，不是景点

`ResolvedPlace` 与 `Attraction` 是**两个类型**，这是结构性保证而不是注释：

| | `Attraction` | `ResolvedPlace` |
| --- | --- | --- |
| 来源 | 数据源搜出来的 POI | 笔记里被提到的名字，再问地理编码器 |
| 评分 / 票价 / 营业时间 | 来源给的实测值 | **没有这些字段**，因为没人测过 |
| 坐标 | 数据集的记录 | 从文字读出来的名字再查出来的读法 |
| 进入行程 | 会被排进某一天 | **不会**。笔记说某人喜欢某处，不等于你决定要去 |

所以「笔记里提到的店」不可能在任何一个消费 `Attraction` 的地方混进去——它不是那个类型。用 `Attraction` 加一个布尔标记是做不到这一点的：那只是一句注释，不是约束。有测试断言它不出现在 `attractions` 里，也不出现在任何一天的 `items` 里。

### 同名地点：目的地是唯一的消歧依据

西湖在杭州，也在惠州和扬州；人民公园在大多数大城市都有。一个只知道名字的地理编码器会返回它排名第一的那个，而那经常不是笔记所指的那个——**这类错误不会报错，它会变成某人星期二行程里的一站**。

两个手段一起用：

1. **查询本身限定范围**。高德接受城市名或 adcode；Nominatim 用 `viewbox` + `bounded=1`——`bounded` 是关键，没有它 `viewbox` 只是影响排序，全局更出名的同名地点照样胜出；有了它，Nominatim 宁可不返回，而不是返回一个错的。
2. **答案按到目的地的距离核对**。超过 80 公里的报为 `elsewhere`，并给出距离。

排序是**先精度、再距离**，顺序不能反：

- 只按距离排会答错问题。西湖区的质心通常比西湖风景名胜区更靠近杭州市中心，于是「离市中心最近的西湖」会赢，而问题本来就是「笔记说的是哪个西湖」。
- 反过来，如果先按精度在**全部**候选里排序，另一个省里一个更精确的结果会顶掉手边可用的近答案，然后被距离检查否掉——一个本来能用的答案被报成了「在别处」。所以距离是**过滤器**，精度是过滤器内部的排序键。

`PlaceCandidate` 因此有两个不同的字段，它们确实是两件事：

- `confidence` — **来源有多确定自己找对了**（进引用，给人看）
- `precision` — **找到的那样东西有多具体**（用于排序）

高德完全可以百分之百确定它找到了西湖区：那是一个确定的匹配，只是找错了东西的种类。

### 四种结果，不是两种

`PlaceResolutionStatus` 有四个值，因为读者的下一步对每一种都不同：

| 状态 | 含义 |
| --- | --- |
| `located` | 找到了，且在目的地范围内，带坐标 |
| `elsewhere` | 找到了，但在别处。**照样报出来并给出距离**——「找不到」和「在 950 公里外」是不同的事实，丢掉前者会看起来像查询失败，接受后者会把一站排到另一个省 |
| `not_found` | 查过了，来源没有这个名称的结果 |
| `not_attempted` | **没有可用的来源，因此根本没查过** |

最后两个必须分开。部分配置的部署（没配高德）会持续产生 `not_attempted`，而把它显示成「没有找到这个地方」就是对地点的一次凭空断言——和「缺失的 `age_unknown_facts` 被当成空数组」是同一类错误。

同理，目的地的坐标拿不到时**不会**用一个假的原点去做距离判断：那要么否掉地球上所有地方，要么接受所有地方，而两者看起来都像答案。这种情况一律报 `not_attempted` 并说明原因。

### 两个来源做同一个决定

`providers/place_matching.py` 是独立模块而不是各自 provider 里的一个函数，原因只有一个：**两个来源会定位同一个地名，它们必须给出同一个答案**。部署了高德的使用者走一条路，没部署的走另一条；如果各自实现判断，两者会漂移，而漂移是不可见的——同一个笔记，一个属主得到坐标，另一个得到拒绝，双方的结果里都没有任何东西显示它们不一致。

`tests/unit/test_place_resolution.py` 里同一个真实同名地点（惠州西湖）会分别走两条路，两边都必须以同样的方式拒绝。

### 地名不做二次修剪

提取出来的名字**原样**送去查询，这里刻意没有「整理一下」的步骤。这一点值得写下来，因为它诱人而且它是错的：`_PLACE_PATTERN` 是非贪婪匹配到**第一个**地名后缀，所以「推荐去灵隐寺看看」到达这里时已经是「灵隐寺」，一个下游修剪器什么都没修，却引入了第二套关于「地名在哪里结束」的规则。

提取器真正的毛病在反方向：后缀本身出现在更长的名字里时会**截短**——断桥残雪 → 断桥，宽窄巷子 → 宽窄巷。那是提取器的限制，修在提取器里；在这里用一个只会截断的启发式去补，只会更糟。两个来源清单都如实写了这条限制。

### 时效性与引用

- 地名索引的**重建时间来源不公布**，所以引用一律是 `observation_basis=source_silent`，只标注我们什么时候问的。用 `live_computed` 等于声称这个名字索引和这次请求一样新，而没人能支持这个说法。
- **`elsewhere` 与 `not_found` 也带引用**。一次查询是一个数据源，它的结果只有在被引用时才能核对；「在别处」没有引用就只是一句断言。
- 这些引用进入计划的 `source_references`，并按 `place_lookup` 参与时效性审计。`MAX_AGE_SECONDS` 里**没有** `place_lookup`——行政区划与 POI 的变化尺度是月，不是小时，而给它一个上限只会制造无意义的警告。
- 逐个地名报告失败，绝不让一个查不到的名字丢掉同一篇笔记里其他名字的结果。

### 没有来源时

`resolve_places` 是一个**能力**（`CAPABILITY_BY_METHOD`），和酒店搜索并列。没有配置任何能提供它的来源时，`ingested_places` 就是空列表，提及照旧以 `matched: false` 列出——这是零配置的默认行为，也是正确的：什么都没被查询过，因此什么都不该被声称。

### 测试与探针

| 文件 | 覆盖 |
| --- | --- |
| `tests/unit/test_place_resolution.py` | 选择与拒绝本身：最近的赢、`elsewhere` 带距离、四种状态互不混淆、精度与置信度分离、无精度排最后、同名并列时结果稳定、两个来源结论一致 |
| `tests/integration/test_ingested_places_in_plan.py` | 真实 HTTP：定位成功、**不变成景点也不进某一天**、引用进入计划、950 公里外的同名报 `elsewhere`、已匹配的提及不被查询、无来源时报 `not_attempted`、属主隔离 |
| `scripts/probe_place_resolution.py` | 对着假地理编码器跑一遍完整判定，打印每个地名的四种结果 |

### 还没做

- 距离用的是**直线距离**。它对「是不是同一个城市」足够，对「走过去多久」不够——所以这里不从它推算任何通行时间。通行时间需要一个路径服务，那是另一个能力。
- 80 公里内有多个同名地点、且精度相同时无法区分。要区分需要一个知道行政归属的来源，免费栈没有这个信息（`GeoResolver` 只给国家和城市）。


### 时效性

`user_content` **刻意不在** `MAX_AGE_SECONDS` 里。一篇写得好的街区指南不会像预报那样按时间表失效——关键是**公开它的年龄**，而不是对它设阈值。给它一个上限只会让每一篇真正有用的旧攻略都触发警告，而读者就是这样学会忽略警告的。

没有标注发布时间的笔记照常走 `SOURCE_SILENT` 路径，被报为「数据时间未知」，不会被当作最新内容。

## 数据模型

`content_ingestions` 表（迁移 `a1f7c93e5b20`）：

- `content_text` 逐字保存输入。提取结果只能对着它核对，而没人能核对的提取是断言而不是引用。
- `published_at` **可空，而这个 null 就是重点**：它记录「页面没有说」。默认成摄取时间会让每篇旧笔记看起来都是新的。
- `facts_json` 用 JSON 而不是子表：一篇笔记的事实总是整块读取，从不单独查询，也从不参与 join。
- 每一行都按 `owner_id` 过滤。保存的笔记会暴露作者在哪吃、何时出行。仓储层把 `None` 读作「不过滤」（脚本与 CLI 用），而 `""` 是一个**真实的属主**，两者必须保持区分——把 `""` 合并进 `None`，一个匿名使用者就能读到另一个的笔记。跨属主读取返回 **404 而不是 403**：确认某个 id 在别的属主下存在，本身就是在泄露它存在。
- `AUTH_ENABLED=false` 时写入的属主**不是 `None`，而是配置的 `AUTH_ANONYMOUS_OWNER`**（默认 `local-dev`，见 `.env.example`），因为「未启用认证」不等于「这份数据没有属主」。早期版本在这里返回 `None`，于是同一次请求里写入用了一个答案、规划时按环境属主查找用了另一个答案，**默认本机模式下保存的笔记永远进不了行程**；带密钥的路径两个答案恰好相同，所以这个缺陷一直看不见。规则现在只有一条：属主就是 principal 的属主。

## API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/v1/ingestions` | 提取并保存。返回提取结果而不只是 id——真正的问题永远是「你从中读到了什么」 |
| `GET` | `/api/v1/ingestions` | 自己的笔记，最新在前 |
| `GET` | `/api/v1/ingestions/{id}` | 单条 |
| `DELETE` | `/api/v1/ingestions/{id}` | 删除 |
| `GET` | `/api/v1/content/bookmarklet` | 书签脚本 |

计划在每次生成时**重新读取**笔记，因此刚保存的立刻生效、删掉的立刻消失。读取失败被吞成空列表：使用者自己的可选笔记，绝不能弄坏行程规划。
