# 凭据保险箱（Credential Vault）

Traver 不提供任何模型，也不内置任何数据源。每个人接入自己的 AI 模型和高德这类平台 Key，是这套程序的基本用法。因此有一个问题必须先回答清楚：**这些 Key 存在哪里，谁能读到，数据库泄露会怎样。**

## 两种凭据，两种机制，故意分开

| | Traver 自己的访问密钥 | 用户接入的第三方 Key |
|---|---|---|
| 表 | `api_keys` | `credentials` |
| 用途 | 只做**校验**，从不重放 | 每次调用都要**重放**给上游 |
| 存储 | SHA-256 摘要（单向） | AES-256-GCM 密文（可逆） |
| 泄露后果 | 拿不到可用密钥 | 必须靠主密钥保护 |

把两者混在一张表里是设计错误：哈希单向，无法重放；明文存储则一旦泄露全部失守。所以它们是两个问题、两套机制。

## 加密方式

- 算法：AES-256-GCM（认证加密）。
- 每次写入生成新的随机 nonce（96 bit），所以**同一个 Key 存两次得到的密文不同**，无法通过比较密文判断两人是否用了同一个 Key。
- **属主、来源、凭据名被绑定为 AAD**（associated data）。这样即使有人拿到数据库写权限，把 A 的密文复制到 B 的行里，解密会**认证失败**而不是把 A 的 Key 交给 B。
- 密文被篡改、截断，同样认证失败并抛错。**绝不返回"看起来像那么回事"的值**——那意味着把错误的凭据发给了上游。

## 主密钥从哪来

按优先级：

1. `CREDENTIAL_ENCRYPTION_KEY`（推荐）。主密钥只存在于进程环境里，不进数据库，也不进数据库备份。
2. `CREDENTIAL_KEY_FILE`（默认 `.traver-credential-key`），首次使用时自动生成，并在支持的平台上设为仅属主可读。

主密钥格式错误时**拒绝启动保险箱**，而不是悄悄生成一个新的——静默换钥从用户视角看等同于"所有凭据凭空消失"。

密钥文件已被 `.gitignore` 忽略，并且有测试断言这一点：主密钥能解开全部凭据，提交它就等于一次性交出所有 Key。

## 它防什么，不防什么

必须说清楚，否则"已加密"三个字会被理解成它做不到的事。

**防：**
- 数据库泄露——备份文件、被拷走的 `.db`、只读 SQL 注入、运维直接翻表、截图。没有主密钥就是密文。
- 篡改与搬移——GCM 认证，改一个字节或换一行都会失败。
- 跨租户越权——每次读取都按 `owner_id` 过滤，且属主绑在 AAD 里。

**不防：**
- 能读取整个文件系统的人（在使用密钥文件模式下）——自动生成的主密钥就放在数据旁边。想避免这种情况就设 `CREDENTIAL_ENCRYPTION_KEY`。
- 能在 API 进程内执行代码的人——他可以直接让保险箱解密。任何静态加密方案都挡不住这一条。
- 被攻陷的主机、恶意依赖、部署里泄漏的环境变量。

一句话：这是**静态数据的纵深防御**，不是"服务器被攻陷也安全"。API 会如实报告当前用的是哪种模式（`/api/v1/health` 的 `credential_key_source`、`/api/v1/providers/catalog` 的 `vault`）。

## 明文永远不出网

- `PUT /api/v1/settings/credentials/{provider}/{key}` 只写入。
- `GET /api/v1/settings/credentials` 只返回**名字和来源**（`stored` / `env`），从不返回值。
- `GET /api/v1/providers/catalog` 同样只报"配没配"。
- 没有任何接口能把已存的 Key 读回来。想看它是否有效，用"测试连接"，那是真发一次请求。

这样设计是因为：把已存密钥再显示出来只增加一条外泄路径，而用户真正的需求是"能不能用"，不是"抄回来"。

## 环境变量与界面配置的关系

`环境变量 = 兜底默认，界面保存 = 覆盖`：

- 运维可以在镜像里写好一套默认值，开箱即用；
- 任何人在界面上保存的值，只覆盖**他自己**；
- 因此同一个部署可以多人使用不同模型、不同 Key。

**一个重要例外**：如果某个值已经存在保险箱里但解不开（主密钥换了或丢了），解析**不会**回退到环境变量的那个 Key。否则用户保存的 Key 一旦失效，他的请求就会悄悄花别人的额度。这种情况一律报错，并出现在 `/ai/chat` 响应的 warnings 里。

配置解析按请求进行，不缓存——所以界面保存**不需要重启**。这不是省事，而是避免"我明明改了却还在用旧 Key"这类最耗人信任的 bug。

## 未配置也是合法状态（渐进增强）

`ai_base_url` 缺失 = 没有模型 = **不是错误**。本地确定性规则引擎会接手，行程照样规划完整，只是少了模型的理解与编排。UI 不应该把这种情况显示成故障。

只有"配了但用不了"才需要报警。这两者必须区分，否则用户分不清是自己没配还是配错了。

本地模型（Ollama / LM Studio 等）**不需要 API Key**，所以模型是否启用只看 `ai_base_url`。早期版本要求 Key 和地址同时存在，导致最常见的自建模型方案根本无法使用。

## 相关接口

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/v1/health` | 保险箱状态与主密钥来源 |
| GET | `/api/v1/providers/catalog` | 能力矩阵、每个源缺哪些凭据、保险箱状态 |
| GET | `/api/v1/settings/credentials` | 本人已配置的凭据名与来源 |
| PUT | `/api/v1/settings/credentials/{provider_id}/{credential_key}` | 保存（只写） |
| DELETE | `/api/v1/settings/credentials/{provider_id}/{credential_key}` | 删除，回退到环境变量 |
| POST | `/api/v1/settings/model/test` | 真发一次请求测试模型连通性 |

写入与删除需要 `trip:write` 作用域。`provider_id` 和 `credential_key` 必须来自 Provider 清单——否则错别字会写进一条永远没人读的记录（表现和"保存成功但没生效"一模一样），保险箱也会变成任意键值存储。
