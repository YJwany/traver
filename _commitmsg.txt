feat: deliverable API with auth, tenancy, rate limiting and CI

Fix the write-gate bypass first, since it was a correctness hole rather than a
missing feature:

* POST /tools/{name} passed allow_write=True unconditionally, so the write
  intent check guarding the AI tool path could be skipped entirely by any caller
  that hit the endpoint directly. The gate now derives from the request, with
  HTTP-level regression tests.
* The write-intent pattern also granted permission on negated phrasing ("do not
  book anything" read as a booking request); negation is now detected before an
  intent is recorded.

Security and tenancy:

* Bearer API keys, stored as SHA-256 hashes with a short display prefix. Trips
  are scoped to the owning principal, so one owner cannot read or modify
  another's itinerary. AUTH_ENABLED defaults off for local work, and
  /api/v1/health reports the active mode so an unsecured deployment is never
  mistaken for a secured one.
* CLI (python -m travel_api.cli) to mint, list and revoke keys.
* Inbound per-client rate limiting with a tighter budget for the AI endpoint.
  The limiter returns a delay instead of raising: an HTTPException raised in
  middleware bypasses FastAPI's handlers and would surface as a 500.
* CORS origins are configurable, and the readiness probe round-trips the
  database instead of reporting liveness.

Engineering:

* Optimistic locking via expected_version (409 on conflict) and bounded list
  pagination.
* Alembic migration for the api_keys table; CI runs upgrade/downgrade/upgrade
  and fails on model-vs-migration drift.
* requirements.lock, a production Dockerfile running non-root from the lock
  file, a prod compose profile, and a healthcheck script with a tested
  exit-code contract.
* .gitattributes normalizes line endings across the Windows dev / Linux CI
  boundary.
* Collapsed ten stale placeholder READMEs in services/ and packages/ into one
  honest file per root: several described already-shipped work as future work.
